# Data engine over sqlc

Status: design, revision 2 (after technical review), approved · 2026-10-21

## Intent

Today every service talks to Postgres by calling sqlc-generated code directly (`store.New(platform.DBFrom(ctx)).X(...)`, 244 call sites in 39 files). sqlc is good at fixed SQL, and it cannot build queries at run time. The ten filterable lists (6 in HRM, 4 in Sales) work around that with catch-all SQL: `(sqlc.narg(x) IS NULL OR col = x)` for each optional filter and one `CASE WHEN @sort = …` per sort key. Adding a filter or a sort key means editing the SQL, the params struct, the Huma filter and its enum. One statement serves every filter combination, so its plan, especially a generic plan once pgx's prepared statement is reused, may not suit the combination actually asked for. This is a risk to measure, not a proven problem.

The product owner wants **one data engine between domain logic and the database**:

- built on sqlc, not replacing it;
- the only way business code reaches the database;
- adding what sqlc lacks: dynamic queries and filters, structured database errors, data-access enforcement, and a seam that does not block tenant-defined fields later.

### Goals

1. A package `internal/platform/data` (the engine) that every module and core service uses for all database access.
2. Fixed queries stay hand-written in each module's `queries.sql` and generated by sqlc. The engine runs them through sqlc's own generated methods.
3. Dynamic lists: a hand-written base query, with filters, search, sort, paging and the permission scope added by the engine at run time.
4. Database errors become stable API error codes, from a per-module constraint map.
5. Enforcement: writes only inside `InTx`, visibility fails closed, no direct database access outside the engine and declared infrastructure.
6. Query logging by name and duration, never with SQL literals or parameter values.

### Non-goals

- No ORM: no change tracking, no schema-from-code, no lazy loading. ADR-0008's "hand-written SQL" stays true.
- No replacement of sqlc, pgx or River. No new dependency.
- No dynamic partial `Update` (writing only changed columns).
- No custom fields, custom entities or custom document types (projects B and C), and no API built for them in advance.
- No new unit of work. `platform.InTx` with the transaction carried in `ctx` already is one.
- No change to transaction boundaries or the document lock order.

### Anti-goals (failure even if it works)

- Any business write leaving the single pgx transaction. This covers record, audit, numbering and River enqueue, which must stay in one commit.
- SQL text assembled from user input, including sort keys, filter names and search text.
- A caller able to widen visibility beyond what IAM granted.
- Breaking the document lock order in `CLAUDE.md` / `documents.md`.
- A second source of schema truth next to `migrations/`.
- Losing `check-queries.mjs` coverage of cross-schema reads.
- Sensitive values appearing in logs or audit.

## Why not an ORM or a query library

Researched 2026-10-20/21. These are recorded for the ADR.

| Option | Why not |
|---|---|
| Ent | Built on `database/sql` only. Its transaction cannot hand a `pgx.Tx` to River ([ent#4295](https://github.com/ent/ent/issues/4295), open, no maintainer answer), which breaks "jobs enqueued in the same transaction". One generated client per entity graph conflicts with module isolation, and its schema-in-Go conflicts with SQL-only migrations. It still needs raw SQL for recursive CTEs and payroll. |
| bob | Closest prior art (queries generated from `.sql` files, `With()` adds mods at run time). It would replace sqlc with a second code generator rather than build on it. |
| squirrel | Declared "complete": slow bug fixes, no features. It only covers the string building, which is the small part. |
| go-jet | Generates from a live database and runs on `database/sql`. |
| Wait for sqlc | Dynamic queries have been "Exploring" on sqlc's roadmap since 2024 ([sqlc#3414](https://github.com/sqlc-dev/sqlc/issues/3414), [discussion #364](https://github.com/sqlc-dev/sqlc/discussions/364)), with no maintainer design. |

The community's most common answer is "sqlc for fixed queries plus a small builder behind a repository-like layer". This design follows that answer.

## Constraints from the repo

- Layers: `platform` must not import `core`, `shared` or `modules` (depguard). The engine lives in `platform` and knows nothing about records, audit or permissions.
- DB access only through `platform.DBFrom(ctx)` / `platform.InTx`. No pool or store kept in a struct, no `pgx.Tx` passed as a parameter.
- Each module's store is in `<module>/internal/store`. Go's `internal` rule keeps it private to the module, and generated engine descriptors live there too.
- `make gen` runs offline (sqlc reads `migrations/`). The plugin must not need a database.
- Tenant isolation is one database per tenant (ADR-0001). The connection in `ctx` already points at the tenant's database. The engine takes no tenant parameter, and org-unit scope works only inside one tenant.
- Money is `int64`, rates are `decimal`, never `float`.
- Error responses are `platform.Error{Code, Params}`, never sentences.

## Architecture

```
module queries.sql                     ← every SQL statement, written by hand
      │ make gen
      ├─ sqlc v1.30.0 gen.go  → store/queries.sql.go   methods, Params, Row structs (unchanged)
      └─ codegen: sqlc-gen-data (process plugin) → store/data.gen.go
                                         names + method references, no types
      │
internal/platform/data                 ← engine
      │  validate → compile → execute → scan
      │  error normalization, data-access enforcement
      │
module and core services               ← call only the engine
```

### Engine structure

The engine holds four stages and two cross-cutting concerns, and nothing else.

| Stage | Responsibility | Never does |
|---|---|---|
| Validator | Checks a list definition at registration and test time: columns exist, sort keys known, scope declared. At run time it checks a query: sort key in the enum, scope sealed, paging bounds. | touch the database |
| Compiler | Turns a validated definition and query into `(sql string, args []any)`. It concatenates trusted fragments and numbers placeholders it allocates itself. | parse or rewrite SQL text |
| Executor | Runs fixed queries through sqlc methods, and compiled queries through `DBFrom(ctx)`. Puts the query name into `ctx` for the tracer. | log, retry, open transactions |
| Scanner | `pgx.CollectRows(rows, pgx.RowToStructByName[R])` for dynamic lists. Fixed queries use sqlc's generated scan. | anything else |

- **Error normalization** maps `PgError` to `platform.Error` (§3).
- **Enforcement** covers the read-only default, the sealed scope and the lint rules (§5, §6).

Business rules, permissions logic, audit, record and domain hooks stay out of the engine.

### 1. Fixed queries and generated descriptors

The plugin is a sqlc process plugin added as a `codegen` entry next to the existing `gen.go` in every `sql` entry of `sqlc.yaml`, writing `data.gen.go` into the same `store` package. It reads only each query's `name`, `cmd` and `len(params)`, plus the `-- data:base` marker. **It maps no types.** It emits one line per query, and Go infers every type from sqlc's own method:

```go
// store/data.gen.go (generated)
var GetEmployee    = data.One1("hrm.GetEmployee", New, (*Queries).GetEmployee)       // :one, 1 arg
var ListLeaveTypes = data.Many0("hrm.ListLeaveTypes", New, (*Queries).ListLeaveTypes) // :many, 0 args
var DeleteLines    = data.Exec1("sales.DeleteLines", New, (*Queries).DeleteLines)     // :exec, 1 arg
```

The eight constructors are `One0/One1`, `Many0/Many1`, `Exec0/Exec1` and `ExecRows0/ExecRows1`. Each is generic over the store's `*Queries`, its `DBTX`, and the argument and result types. Nullable columns, type overrides, `RETURNING`, CTEs and `pgtype` values are whatever sqlc generated. A signature that does not fit makes the generated file fail to compile, so drift is caught by `make gen` in CI.

```go
row, err := data.Get(ctx, store.GetEmployee, id)        // was store.New(platform.DBFrom(ctx)).GetEmployee(ctx, id)
rows, err := data.Many(ctx, store.ListLeaveTypes)
err = data.Exec(ctx, store.DeleteLines, docID)
```

Each call takes `DBFrom(ctx)`, puts the name into `ctx`, calls the sqlc method and normalizes the error. `pgx.ErrNoRows` passes through unchanged.

**Plugin wiring.** `make gen` builds the plugin with `go build -o` into a repo-local, gitignored path, then runs pinned sqlc. The plugin's `process.cmd` points at that path. sqlc clears the environment and resolves the command with `exec.LookPath`, so the path is relative to the repo root (assumption, confirmed in the spike). CI's "`make gen` leaves no diff" covers `data.gen.go`. A command other than the four above makes the plugin fail generation with a message.

### 2. Dynamic lists

#### Base query

```sql
-- name: LeaveListBase :many
-- data:base
SELECT r.id, d.number, d.status, d.org_unit_id, e.user_id, r.employee_id,
       e.code AS employee_code, e.full_name AS employee_name, t.name AS leave_type_name,
       r.start_date, r.end_date, r.days::text AS days
FROM hrm.leave_requests r
JOIN record.documents d ON d.id = r.id
JOIN hrm.employees e ON e.id = r.employee_id
JOIN hrm.leave_types t ON t.id = r.leave_type_id;
```

- It is hand-written in `queries.sql`, type-checked by sqlc and scanned by `check-queries.mjs` like any other query.
- **It takes no parameters.** The plugin fails generation for a `-- data:base` query with parameters. Everything that varies (filters, today's date, the actor) is added by the compiler, which numbers all placeholders itself starting at `$1`. Nothing is renumbered.
- Columns used by scope, filters, search or sort must be in its select list. Output names must be unique after pgx's normalization (lower case, `_` removed). The validator checks this.
- The compiler wraps it as `FROM (<base>) b`. Whether Postgres flattens the subquery or pushes predicates into it depends on the base's shape, and is verified per list (§Performance), not assumed. A list whose plan is not acceptable either has its base reshaped or stays on a fixed query.

#### Trusted SQL fragments

```go
type Static string                       // untyped string constants convert implicitly; string variables do not
func SQL(s Static) Frag                  // starts a fragment
func (f Frag) Arg(v any) Frag            // appends a bound value
func (f Frag) Text(s Static) Frag        // appends more static text

data.SQL(`b."end_date" >= `).Arg(from)
data.SQL(`b."id" NOT IN (WITH RECURSIVE under(id) AS (SELECT `).Arg(m).
    Text(`::bigint UNION SELECT s.id FROM hrm.employees s JOIN under ON s.manager_id = under.id) SELECT id FROM under)`)
```

- Every text parameter is of the named type `Static`, so only literals and constants compile there. A `string` variable needs an explicit `data.Static(x)` conversion, which lint bans outside `platform/data` (§6). Fragments are therefore literals written in code, and every value goes through `Arg`. *Verified by Go's assignability rules for untyped constants. The spike adds a compile-fail fixture.*
- There are no `?` placeholders, no SQL scanning, and no handling of quotes, comments, `$$` strings or `::` casts.
- Column references in definitions are names checked against the base's output columns and emitted as `b."<name>"`.

#### List definition

```go
type List[R any] struct {
    Name       string             // "hrm.LeaveList", for logs
    Base       Base[R]            // generated from the -- data:base query
    Scope      ScopeRule          // required: data.ByColumn("org_unit_id") or data.Unscoped("tenant-wide catalogue")
    Visibility func(v Viewer) Cond // optional, static; extra rows visible outside the units (OR'd)
    Search     []string           // text columns searched by Q
    Sorts      map[string][]Order // sort key ("start_date", "-start_date") → ORDER BY terms
    Default    []Order
    Tiebreak   Order              // unique column, with direction (e.g. Desc("id"))
}

type Order struct{ /* column, direction, lower, nulls */ } // Asc("code").Lower(), Desc("end_date").NullsLast()

type Query struct {
    Scope  data.Scope        // sealed; only IAM can build a non-empty one
    Q      string
    Sort   string
    Paging platform.Paging
    Where  Cond              // filters from the typed Huma filter struct
}

func (l List[R]) Run(ctx context.Context, q Query) (Page[R], error)
type Page[R any] struct{ Items []R; Total int64 }
```

Lists are package-level values registered with `data.Register(list)`. The validator runs at registration, so a bad definition panics at startup and fails every test that builds the service.

#### Scope: fail-closed

- **`data.Scope` is sealed.** Its fields are unexported. The zero value grants nothing. The constructors (`data.GrantAll`, `data.GrantUnits`) are banned by lint outside `internal/core/iam` and tests (§6). A new `iam.(*Service).DataScope(ctx, product, perm)` returns a `data.Scope` (today's `Scope` stays for other uses), so the permission check that produced it is IAM's, and callers cannot widen it.
- **Every list declares its rule.** `ByColumn(col)` or `Unscoped(reason)`. There is no default. A list without a rule fails validation.
- **`Visibility` is part of the definition, not the call.** It receives a `Viewer` that the engine builds from `platform.ActorFrom(ctx)`. The caller supplies nothing to it. Leave and overtime declare it statically:

  ```go
  Visibility: func(v data.Viewer) data.Cond {
      return data.Or(
          data.SQL(`b."user_id" = `).Arg(v.Actor),
          data.SQL(`b."employee_id" IN (WITH RECURSIVE down AS (… WHERE me.user_id = `).Arg(v.Actor).Text(` … ) SELECT id FROM down)`),
      )
  }
  ```

  This replaces the service-side `Reports` lookup with the same SQL inlined, so it is one round trip instead of two.
- **Compiled condition:** `(<scope> OR <visibility>)`.
  - `GrantAll` makes it `TRUE`.
  - With `GrantUnits`, the scope part is `b."org_unit_id" = ANY($n)`.
  - With no units, there is no scope part. If there is no `Visibility` either, the engine returns an empty page without querying.
  - `Unscoped` lists ignore `Query.Scope`. `data.Unscoped` is allowed only in definitions, never in a call.
- Tenant isolation does not depend on any of this. It is the database in `ctx` (ADR-0001).

#### What `Run` compiles

```sql
SELECT b.* FROM (<base>) b
WHERE (b."org_unit_id" = ANY($1) OR b."user_id" = $2 OR b."employee_id" IN (…$3…))
  AND (b."number" ILIKE $4 OR b."employee_code" ILIKE $4 OR b."employee_name" ILIKE $4)
  AND b."end_date" >= $5
ORDER BY b."start_date" DESC, b."id" DESC
LIMIT $6 OFFSET $7
```

- `Q` is trimmed. `%`, `_` and `\` are escaped, then the value is bound once as `%q%`.
- `Sort` must be a key of `Sorts` (the Huma enum already guarantees this at the API). Otherwise the validator returns `invalid_request`. Empty means `Default`. The tiebreak is always appended.
- **Count.** The total comes from a separate `SELECT count(*) FROM (<base>) b WHERE <same conditions>`, sent in the same `pgx.Batch` as the page, so it is one round trip.
  - Skip: on the first page (`OFFSET 0`), if the page holds fewer rows than the limit, the total is the row count and no count is sent.
  - A page past the end now returns the true total. This is a deliberate behaviour change.
  - The spike benchmarks this against `count(*) OVER ()` (§Performance). If the window wins clearly, it may be kept with a fallback count when the page is empty.
- **Scan.** Rows are scanned with `pgx.RowToStructByName[R]` into sqlc's base row type: no embedding, no `db` tags, no extra column.

#### Service code after migration

```go
func (s *Service) Leaves(ctx context.Context, f LeaveFilter) (LeaveList, error) {
    sc, err := s.d.IAM.DataScope(ctx, "hrm", PermLeaveView)
    if err != nil { return LeaveList{}, err }
    page, err := leaveList.Run(ctx, data.Query{
        Scope: sc, Q: f.Q, Sort: f.Sort, Paging: f.Paging,
        Where: data.And(
            data.When(f.Status != "", data.Eq("status", f.Status)),
            data.When(f.OrgUnitID != 0, data.Eq("org_unit_id", f.OrgUnitID)),
            data.When(f.EmployeeID != 0, data.Eq("employee_id", f.EmployeeID)),
            data.When(f.From != nil, data.Gte("end_date", f.From)),
            data.When(f.To != nil, data.Lte("start_date", f.To)),
        ),
    })
    // map page.Items as today
}
```

`Eq/In/Gte/Lte/IsNull/And/Or/When` take a column name, checked against the base when compiling, and a bound value. Huma filter structs, OpenAPI, the frontend `ListParams` and saved views (ADR-0031) are unchanged.

### 3. Structured database errors

- **Classification** in `platform`, by SQLSTATE:

  | Class | SQLSTATE |
  |---|---|
  | unique | `23505` |
  | foreign key | `23503` |
  | check | `23514` |
  | not null | `23502` |
  | serialization | `40001` |
  | deadlock | `40P01` |
  | lock timeout | `55P03` |
  | query canceled | `57014` |
  | read-only violation | `25006` |

- **Constraint map per module**, keyed `schema.constraint`, registered at startup:

  ```go
  data.RegisterConstraints(data.Constraints{
      "sales.customers_code_key": ErrCustomerCodeTaken,
      "sales.items_code_key":     ErrItemCodeTaken,
  })
  ```

  - Re-registering the same pair is a no-op, because test binaries build services many times. A conflicting pair panics.
  - Only constraints with **one meaning everywhere** are mapped. Context-dependent ones (e.g. `hrm.leave_balances_days_check` → two different errors, approval → `record.ErrAwaitingApproval`) stay unmapped, and their call sites keep `platform.Violates`.
- **Translation:**
  - a mapped constraint becomes its `*platform.Error`, wrapping the `PgError`, so `Violates` and `errors.As` still match;
  - unmapped errors are returned wrapped and reach the API as `internal_error`, logged by the existing handler;
  - `data.IsRetryable(err)` reports serialization and deadlock errors. There is no automatic retry.
- `25006` (a write on a read-only session) is a programming error. It maps to `internal_error` and is logged with the query name.

### 4. Query logging

- The executor puts the query name (and, for lists, a **shape**: active filter names plus the sort key, all from code) into `ctx`. One `pgx.QueryTracer` on each pool reads it in `TraceQueryStart`/`TraceQueryEnd`. **Only the tracer logs**, once per query.
- Logged fields: name, shape, duration, rows affected, SQLSTATE on error. Queries without a name (River internals, migrations) log as `unnamed` at `debug` only.
- **SQL text and parameter values are never logged, at any level**, including debug in production. Golden tests cover the SQL text instead.
- A `warn` for queries slower than a configured threshold. The tracer measures database execution as pgx sees it, which includes network time.

### 5. Write enforcement

The guard does not classify SQL. Postgres enforces it.

1. **App pool sessions default to read-only:** `default_transaction_read_only=on` in the pool's runtime params.
2. **`platform.InTx` begins with `pgx.TxOptions{AccessMode: pgx.ReadWrite}`.** It is the only way to get a writable transaction.
3. **Any write outside `InTx` fails with `25006`**, whatever its form: `INSERT/UPDATE/DELETE`, a data-modifying CTE, `SELECT … FOR UPDATE/SHARE`, `nextval`, or a function that writes. *Assumption: per Postgres documentation of read-only transactions. The spike must prove each case with a test.*
4. **River gets its own pool** (normal sessions), since it writes outside our transactions. The client keeps `InsertTx` with our transaction, so enqueue stays inside the business transaction. A second pool is still "one Go binary + Postgres".
5. **`platform.Enqueue` requires a transaction in `ctx`**, and returns an error instead of falling back to a non-transactional insert. A request that enqueues a job and writes nothing else wraps it in `InTx`, which costs one `BEGIN/COMMIT`.
6. **Infrastructure exceptions,** each documented in code:
   - migrations: own connection, read-write;
   - `pgtest`/`coretest` setup;
   - `create-admin` (through `InTx`);
   - River's pool.

Existing writes outside `InTx` (if any, e.g. session or login bookkeeping) will fail tests with `25006`. That is how they are found, and they get wrapped in `InTx`. Audit, numbering and `record` already run inside the caller's transaction, so they inherit the rule.

### 6. Lint enforcement

The existing depguard `no-pool` rule stays. Added rules, with the infrastructure allowlist (`internal/platform/**`, `internal/app/**`, `cmd/**`, `**/pgtest/**`, `**/coretest/**`, generated `*.gen.go` and `queries.sql.go`):

| Rule | Tool |
|---|---|
| `store\.New` banned | forbidigo |
| `platform\.DBFrom` banned (after a module migrates) | forbidigo |
| `\.Begin(Tx|Func)?\(`, `pgx\.BeginFunc` banned | forbidigo |
| `platform\.JobsFrom`, `\.Insert(Tx)?\(` on River clients banned outside `platform` | forbidigo |
| `data\.Static\(`, `data\.GrantAll`, `data\.GrantUnits` banned outside `platform/data` and `core/iam` | forbidigo |
| `github.com/riverqueue/river` client construction only in `internal/app` | depguard |

The `store.New` and `DBFrom` bans are switched on per module as it migrates. Once all modules have moved, the exclusions go away. Each rule gets a planted violation in a lint fixture, as `check-queries.mjs` does, so a misconfigured pattern fails CI.

## Readiness for custom fields and entities (projects B and C)

Project A builds **none** of B or C, and adds no API for them. It keeps the shape that makes them possible:

- The compiler works on column descriptors that are data (name, type, expression built by the compiler). Generated columns and future run-time columns can share that path.
- Fragments and values stay separated (`Static` and `Arg`), so a later run-time column never needs SQL text from users.
- Base queries come only from `queries.sql`. B's generic tables will get fixed base queries like any other.
- The constraint registry is a map that B can extend.

Questions handed to B, all unverified:

- A JSON key bound as a parameter may prevent matching an expression index such as `(custom->>'size')` under a generic plan.
- Casting malformed JSON values (`::numeric`, `::date`) raises an error for the whole query, not for the row.
- A missing key and a JSON `null` both read as SQL `NULL`.
- Money must stay `int64`: JSON numbers must not pass through `float64`.
- Per-field permissions.

## Document lines (`SyncLines`)

Not built in this project. Today lines are replaced on each draft save:

- Sales: `DeleteLines`, then one `InsertLine` per line.
- HRM: `DeleteTimesheetLines`, then one `INSERT … SELECT unnest(…)`.

This is correct because lines are editable only while the document is a draft (ADR-0027). No other document can reference a draft's lines, and the posted documents that later deliveries or invoices will reference never change. So:

- **Now:** Sales line inserts become one batched statement (an `unnest` insert, like timesheets), cutting N round trips to one.
- **When delivery or invoicing arrives:** `sales.lines` gets an `id` identity column as the foreign-key target, in a new migration. Draft lines keep being replaced, and changing ids are harmless while nothing points at a draft.
- **Revisit `SyncLines`** (diff by key, batched insert/update/delete, per-line audit) only if per-line edit history of drafts becomes a requirement.

## Behaviour changes

The migrated lists keep their filters, sort orders (including `lower()`, `NULLS LAST`, per-list tiebreak direction and the payroll list's fixed three-column order) and visibility. The existing service and Playwright tests must pass, except for these deliberate changes:

- **Search escaping.** `%`, `_` and `\` in `q` are matched literally; today they are wildcards. HRM and the Sales quotation/order lists now trim `q`, as the other Sales lists already did.
- **Total past the end.** A page past the end returns the true total instead of 0.
- **Writes outside `InTx` fail** (`25006`), and `Enqueue` outside a transaction errors.

## Performance and correctness verification

Applied in the spike, the vertical slice and every migrated list.

- **Data:** `make seed`, scaled up to production-like volumes for the measured tables (the target sizes are recorded in the PR). Measured with statistics fresh (`ANALYZE`).
- **Plans:** `EXPLAIN (ANALYZE, BUFFERS)` of the old and new query for representative filter combinations:
  - no filter;
  - one selective filter;
  - search;
  - each sort;
  - restricted scope;
  - a page deep in the list.

  Each combination is run under `plan_cache_mode = force_custom_plan` and `force_generic_plan`, because pgx caches prepared statements.
- **Recorded per combination:**
  - planning and execution time;
  - shared hit and read buffers;
  - rows scanned versus returned;
  - p50 and p95 latency over at least 200 runs after 20 warm-up runs, sequential and at 8 concurrent clients (throughput);
  - Go allocations per call (`-benchmem`).
- **Statement cache:** count distinct statements per list under the test matrix, and confirm they stay well under pgx's per-connection cache size.
- **Regression** means p95 worse by more than 20%, or buffers more than doubled, on any combination, without an explained cause. A sequential scan is not by itself a regression on small tables. A list that regresses and cannot be fixed by reshaping its base stays on a fixed query.
- **Correctness:** for each combination, the old and new queries return the same ids in the same order (except for the deliberate changes above), checked by a test that runs both during migration.

## Spike results (2026-10-21)

The spike ran on branch `spike/data-engine` (commits `50285cf`, `d856006`, `b25f17f`, `dc5969c`). That branch is not merged. All four answers are yes.

**S1. Plugin next to `gen.go`: yes.**
- `make gen && go build ./...` exits 0. All 14 `data.gen.go` files compile, and all 262 queries fit the 8 shapes (`:one`, `:many`, `:exec` and `:execrows`, each with 0 or 1 argument).
- The plugin uses sqlc's `process.format: json` with `encoding/json`. It imports neither sqlc nor protobuf, and `go.mod` is unchanged.
- The module name comes from `settings.queries[0]` (the parent directory of `queries.sql`).
- The relative command `./bin/sqlc-gen-data` resolves even though sqlc clears the environment.
- `make gen` time with warm caches stays at about 1.7 s.
- Offline: `GOPROXY=off` already failed before this change, because `go run sqlc@v1.30.0` looks up deprecation info. `GOPROXY=file://$(go env GOMODCACHE)/cache/download` works.
- **Change for Task 4:** a Go package cannot declare both a func `One0` and a type `One0`. The constructors keep their names (`One0` … `ExecRows1`); the types become `One0Query[R]`, `One1Query[P, R]` … `ExecRows1Query[P]`.

**S2. `RowToStructByName` on the base shapes: yes.**
- Leave, employees, contracts, customers and sales headers all scan with no error into structs shaped like sqlc rows (no `db` tags). The values equal those from sqlc's own scan.
- Types covered: `pgtype.Date`, `pgtype.Text`, `numeric::text` and `bigint` money. No new aliases were needed.
- Scanning into the generated base row types is still to be confirmed, in Task 10.

**S3. Read-only sessions: yes.**
- Outside a transaction, these fail with `25006`: `INSERT`, `UPDATE`, `DELETE`, a data-modifying CTE, `FOR UPDATE`, `FOR SHARE`, `nextval`, and a function that writes. All succeed inside a `ReadWrite` transaction.
- `pg_advisory_xact_lock` is allowed outside.
- **Correction:** `CREATE TEMP TABLE` is also refused outside a transaction, as DDL. No code uses temp tables.
- **Census of writes outside `InTx`** (Task 2 wraps each in `InTx`). There are 8 production paths:
  - the job-end notification (`notification.JobEnded`, through `platform/jobs.go:71`);
  - the dataio cleanup job (`dataio/jobs.go:308`);
  - the attachment download audit (`attachment/service.go:189`);
  - the failed-login audit (`iam/service.go:122`);
  - `iam.SetLocale`;
  - `iam.SetListSettings`;
  - `notification.MarkRead`;
  - `notification.MarkAllRead`.

  The two job paths fail because job workers receive the app pool through `env.context`. On the test side: 7 test calls rely on a caller's transaction, and 18 seeding sites write straight to the pool. Those 18 are covered by one writable seeding helper, `pgtest.System`. Two tests built River clients on the per-test pool; they must use the system pool.

**S4. Count strategy: (c).** The count runs in the same `pgx.Batch` and is skipped when the first page is not full.
- At 200 000 rows with no filter, `count(*) OVER ()` is slower at every page tested (page 1: p95 430 ms vs 252 ms; page 50: 416 ms vs 187 ms). Its WindowAgg spills to disk at the default `work_mem`.
- It also returns `Total = 0` whenever the page is empty.
- With a selective filter, every strategy stays under 1.2 ms at p95.
- **Note for the vertical slice:** an unfiltered page at 200 000 rows takes 160–240 ms. The slice must examine indexes on the sort columns.

## Vertical slice results (2026-10-22)

The leave request list runs on the engine (commit `b676cbb`). Engine commits run from `cadb083` to `bee23dc`.

**Correctness.**
- Old and new were compared on 1 224 combinations: 6 actors (admin, scoped HR, a manager two levels deep, a plain employee, a user with no employee, …) × every filter, search, sort and paging case.
- The same ids come back in the same order. Totals match, except a page past the end, which now returns the true total. That is a deliberate change.
- The old query `ListLeaveRequests` is removed. `Reports` was removed when the overtime list moved to the engine.

**Visibility shape (implementation ruling).** The actor's own requests and their reports' requests are one condition: `b."employee_id" = ANY(ARRAY(<the actor's employee and everyone below it, recursive>))`. The actor is bound as a parameter.
