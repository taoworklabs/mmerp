# 0038. Data engine over sqlc: dynamic parts compiled from code-declared fragments, no ORM

Status: accepted · 2026-10-21 · amends ADR-0008 (data access)

## Context

Every service talks to Postgres by calling sqlc-generated code directly (`store.New(platform.DBFrom(ctx)).X(...)`, 244 call sites in 39 files). sqlc is good at fixed SQL and cannot build queries at run time. The ten filterable lists (6 in HRM, 4 in Sales) work around that with catch-all SQL — `(sqlc.narg(x) IS NULL OR col = x)` per optional filter, one `CASE WHEN @sort = …` per sort key. Adding a filter or a sort key means editing the SQL, the params struct, the Huma filter and its enum. One statement serves every filter combination, so its plan — especially a generic plan once pgx reuses a prepared statement — may not suit the combination actually asked for; this is a risk to measure, not a proven problem.

The product owner wants one data engine between domain logic and the database: built on sqlc, not replacing it; the only way business code reaches the database; adding what sqlc lacks — dynamic queries and filters, structured database errors, data-access enforcement — without blocking tenant-defined fields later (projects B and C, out of scope here).

ORMs and query builders were researched (Ent, bob, squirrel, go-jet, waiting on sqlc's own roadmap item); see "Options not taken" below. None fits without breaking an existing constraint (hand-written SQL, module isolation, `pgx.Tx` shared with River in one transaction, SQL-only migrations).

## Decision

Add `internal/platform/data`, the data engine, as the only way module and core services reach the database. It is built on sqlc, pgx and River; no new dependency, no ORM (no change tracking, no schema-from-code, no lazy loading), no dynamic partial `Update`, no custom fields or entities. It does not change transaction boundaries or the document lock order.

**Engine structure.** Four stages, run in order, plus two cross-cutting concerns: Validator (checks a list definition at registration, and a query at run time: columns exist, sort key known, scope sealed; paging bounds are Huma's job, not the validator's), Compiler (turns a validated definition and query into `(sql string, args []any)`; never parses or rewrites SQL text), Executor (runs fixed queries through sqlc methods and compiled queries through `DBFrom(ctx)`; never logs or opens transactions itself), Scanner (`pgx.CollectRows` with `RowToStructByName` for dynamic lists; fixed queries keep sqlc's own scan). Error normalization and write/scope enforcement sit across all four. Business rules, permissions logic, audit, record and domain hooks stay out of the engine.

**Fixed queries.** Queries stay hand-written in each module's `queries.sql`, type-checked by sqlc as today. A sqlc process plugin, run offline as a `codegen` step next to `gen.go`, reads only each query's name, `cmd` and argument count and emits one descriptor line per query using eight generic constructors (`One0/One1`, `Many0/Many1`, `Exec0/Exec1`, `ExecRows0/ExecRows1`), each generic over the store's `*Queries` and the argument/result types sqlc already generated. The plugin maps no SQL types itself — Go infers them from sqlc's own method signature — so nullability, overrides, `RETURNING` and `pgtype` values stay exactly what sqlc generated, and a signature mismatch fails `make gen` in CI rather than drifting silently. Business code calls the generated descriptor's own method, `store.X.Run(ctx, p)` (descriptor types `One0Query[R]`, `One1Query[P,R]`, `Many0Query[R]`, `Many1Query[P,R]`, `Exec0Query`, `Exec1Query[P]`, `ExecRows0Query`, `ExecRows1Query[P]`); each call resolves `DBFrom(ctx)`, puts the query name on `ctx` for the tracer, and normalizes the error (`pgx.ErrNoRows` passes through unchanged).

**Dynamic lists.** A base query is hand-written in `queries.sql`, marked `-- data:base`, scanned by `check-queries.mjs` like any other query, and takes no parameters — everything that varies (filters, scope, search, sort, paging) is added by the compiler, which numbers every placeholder itself starting at `$1`; nothing is renumbered and no SQL text is parsed or rewritten anywhere. Fragments are built only from `Static`, a named string type that only literal/constant text can satisfy, plus bound `Arg` values — there is no string concatenation path from a `string` variable into SQL text, so no path from user input into SQL text either. A list definition (`Name`, `Base`, `Scope`, optional `Visibility`, `Search`, `Sorts`, `Default`, `Tiebreak`) is registered once at package level; the validator runs at registration, so a bad definition panics at startup and fails every test that builds the service. Scope is fail-closed: `data.Scope` is sealed (unexported fields, zero value grants nothing), built only by IAM through a new `DataScope(ctx, product, perm)`; its constructors (`GrantAll`, `GrantUnits`) are banned outside `platform/data` and `core/iam` by lint; every list must declare a `Scope` rule (`ByColumn` or `Unscoped`, with no default) or validation fails; `Visibility` is part of the static definition, never supplied per call. Page 1 runs alone, and its `SELECT count(*)` only follows, as a second round trip, once page 1 comes back full — a page shorter than the limit already is the true total; every later page sends its page and count together in one `pgx.Batch`. A page past the end now returns the true total instead of 0 — a deliberate behaviour change from today's `count(*) OVER ()`. Rows are scanned straight into sqlc's own base row type with `pgx.RowToStructByName` — no embedding, no `db` tags, no extra column. Huma filter structs, OpenAPI, the frontend `ListParams` and saved views are unchanged by this.

**Structured database errors.** SQLSTATEs are classified once in `platform/data` (unique, foreign key, check, not null, serialization, deadlock, lock timeout, query canceled, read-only violation). A per-module constraint map, keyed `schema.constraint`, is registered at startup and covers only constraints with one meaning everywhere; context-dependent constraints stay unmapped and keep using `platform.Violates` at the call site. A mapped constraint becomes its `*platform.Error` wrapping the underlying `PgError`, so `Violates`/`errors.As` still match; unmapped errors reach the API as `internal_error`. `data.IsRetryable` reports serialization and deadlock errors with no automatic retry.

**Query logging.** The executor carries the query name, and for lists a shape (active filter names plus sort key, built from code, never from input), on `ctx`; only a `pgx.QueryTracer` on each pool logs, once per query, with name, shape, duration, rows affected and SQLSTATE on error. SQL text and parameter values are never logged, at any log level, including debug.

**Write enforcement.** Postgres enforces it, not SQL classification in code: app pool sessions default to `default_transaction_read_only=on`; `platform.InTx` is the only way to open a writable transaction (`pgx.TxOptions{AccessMode: pgx.ReadWrite}`); any write outside `InTx` — `INSERT/UPDATE/DELETE`, a data-modifying CTE, `SELECT … FOR UPDATE/SHARE`, `nextval`, a writing function — fails closed with SQLSTATE `25006`. River gets its own normal (read-write) pool, since it writes outside business transactions; `InsertTx` still carries jobs inside the caller's `InTx`, so enqueue stays in the business transaction. `platform.Enqueue` requires a transaction already in `ctx` and errors instead of silently inserting outside one. Infrastructure keeps documented exceptions: migrations, `pgtest`/`coretest` setup, `create-admin` (through `InTx`), River's own pool.

**Lint enforcement.** New forbidigo/depguard rules, with an infrastructure allowlist, ban: `store.New` (per module, once migrated); `platform.DBFrom` (per module, once migrated); `.Begin(Tx|Func)?(`/`pgx.BeginFunc`; direct `.Insert(Tx)?(` on River clients outside `platform`; `data.Static(`, `data.GrantAll`, `data.GrantUnits` outside `platform/data` and `core/iam`; River client construction outside `internal/app`.

### Options not taken

| Option | Why not |
|---|---|
| Ent | Built on `database/sql` only. Its transaction cannot hand a `pgx.Tx` to River ([ent#4295](https://github.com/ent/ent/issues/4295), open, no maintainer answer), which breaks "jobs enqueued in the same transaction". One generated client per entity graph conflicts with module isolation, and its schema-in-Go conflicts with SQL-only migrations. It still needs raw SQL for recursive CTEs and payroll. |
| bob | Closest prior art (queries generated from `.sql` files, `With()` adds mods at run time). It would replace sqlc with a second code generator rather than build on it. |
| squirrel | Declared "complete": slow bug fixes, no features. It only covers the string building, which is the small part. |
| go-jet | Generates from a live database and runs on `database/sql`. |
| Wait for sqlc | Dynamic queries have been "Exploring" on sqlc's roadmap since 2024 ([sqlc#3414](https://github.com/sqlc-dev/sqlc/issues/3414), [discussion #364](https://github.com/sqlc-dev/sqlc/discussions/364)), with no maintainer design. |

The community's most common answer is "sqlc for fixed queries plus a small builder behind a repository-like layer." This decision follows that answer.

## Consequences

- Business code reaches the database only through `internal/platform/data`; `store.New`/`DBFrom` call sites are migrated module by module and then banned by lint.
- Migrated lists keep their filters, sort orders and visibility, with three deliberate behaviour changes: search (`q`) now matches `%`, `_` and `\` literally instead of as wildcards, and HRM trims `q` as Sales already does; a page past the end returns the true total instead of 0; a write outside `platform.InTx`, including through `platform.Enqueue`, now fails instead of silently succeeding non-transactionally.
- Sessions default to read-only and `InTx` is the only writable path, so any existing write outside `InTx` will start failing with SQLSTATE `25006` and must be wrapped in `InTx`; River moves to its own read-write pool while `InsertTx` keeps job enqueue inside the business transaction.
- Database errors on mapped constraints become stable `platform.Error` codes instead of being inspected ad hoc; `Violates` keeps working unchanged for unmapped ones.
- SQL text and parameter values never reach logs, at any level; only query name, shape and duration do.
- No ORM, no new dependency, no change to transaction boundaries or the document lock order; custom fields and entities (projects B and C) build on this engine's column-descriptor and fragment/value separation later, but add no API now.
- `backend.md` and the `new-module` skill are updated to describe the engine and the fixed-vs-dynamic read path in a later step of this work, not by this ADR.
