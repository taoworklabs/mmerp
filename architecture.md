# Architecture overview

The big picture of mmerp in diagrams. This document does not replace the detailed docs: each section has only a diagram, a few key points, and links to where the full description lives. When a diagram and a detailed doc disagree, the detailed doc is right.

## 1. The system in context

```mermaid
flowchart LR
  user["Users<br/>HR, accountants, managers, employees"]
  subgraph site ["Organisation's server (on-premise)"]
    app["mmerp<br/>one Go binary<br/>API, frontend, worker"]
    pg[("Postgres<br/>data, sessions, job queue")]
    disk[("File directory<br/>attachments, backups")]
  end
  vendor["External providers<br/>e-invoices, SMS, email"]
  ours["Monitoring endpoint<br/>receives heartbeats (not built yet)"]
  user -- "browser, HTTPS" --> app
  app --> pg
  app --> disk
  app -. "only through jobs, tolerates Internet loss" .-> vendor
  app -. "outbound heartbeat, can be turned off (planned)" .-> ours
```

- There is only **one binary and Postgres**. No Redis, no broker, no sidecar container ([techstack.md](./techstack.md#constraints)).
- No business operation needs the Internet. Every outbound call goes through a job ([platform.md](./platform.md#integrations)).
- A hosted multi-tenant deployment runs the same binary (see [section 10](#10-deployment-and-tenancy)).
- The heartbeat is not built yet; it comes in [M10](./roadmap.md#m10-on-premise-operations) ([platform.md](./platform.md#operations)).

## 2. Inside the binary

```mermaid
flowchart TB
  subgraph bin ["mmerp binary"]
    spa["React frontend<br/>prebuilt, embedded"]
    http["HTTP: chi + Huma<br/>/api and OpenAPI"]
    mw["Middleware<br/>session, DB into context,<br/>enabled products, X-Authz-Version"]
    wire["internal/app<br/>composition root"]
    mods["Modules<br/>core, shared, modules"]
    workers["River worker"]
    mig["Migration runner<br/>runs at startup"]
  end
  db[("Postgres")]
  http --> mw --> mods
  workers --> mods
  wire -. "wires deps, hooks" .-> mods
  mods --> db
  workers --> db
  mig --> db
```

- At startup: migrate in one transaction (transaction-scoped advisory lock), and only then open HTTP and start the workers. The automatic backup before migrating is not built yet ([tenancy.md](./tenancy.md#update-procedure-on-premise)).
- Services never hold a DB variable; the DB always comes from the context ([backend.md](./backend.md#transactions)).

## 3. Backend layers

```mermaid
flowchart TB
  wire["internal/app<br/>wires deps, hooks, no-op versions"]
  subgraph mods ["modules: per enabled product"]
    hrm["hrm"]
    next["later products"]
  end
  subgraph shr ["shared: always on"]
    posting["posting"]
  end
  subgraph cor ["core: always on, business-agnostic"]
    iam["iam"]
    setting["setting"]
    numbering["numbering"]
    audit["audit"]
    record["record"]
    approval["approval"]
    dataio["dataio"]
  end
  plat["platform: no tables"]
  mods --> shr --> cor --> plat
  approval --> record
  hrm -. "never import each other;<br/>deps.go, hooks.go wired in internal/app" .- next
  wire -.-> mods
```

- Dependencies only point down. Within `modules`, modules never import each other ([backend.md](./backend.md#layers)).
- A lower module that needs to call upward (such as `record` asking `approval`) defines an interface in its `hooks.go`.
- `deps.go` holds required dependencies, never with a no-op version; `hooks.go` holds optional reactions, which may be no-ops ([backend.md](./backend.md#rules-between-modules)).

## 4. One module

```
internal/modules/hrm/
├── module.go       Module(s *Service) → platform.Module: the only entry point
├── service.go      exported methods for other modules
├── types.go        exported types
├── deps.go         Deps struct + interfaces needed from other products
├── handler.go      HTTP, not exported
├── queries.sql     the module's SQL, code generated by sqlc
└── internal/store/ generated code; other modules cannot import it
```

A file that would be empty is left out: `hrm` emits no hooks yet, so it has no `hooks.go`.

```mermaid
flowchart LR
  subgraph hrmmod ["hrm module"]
    h["handler"] --> s["service"] --> st["store (sqlc)"]
  end
  st -- "writes" --> sh[("hrm schema")]
  st -. "read only, join" .-> other[("iam, record schemas")]
  s -- "writes through the service" --> rec["record"]
  rec --> rs[("record schema")]
```

- Each module has one Postgres schema with the same name; only the owning module writes to it. Reads may join across schemas ([backend.md](./backend.md#rules-between-modules)).

## 5. A request that writes a document

```mermaid
sequenceDiagram
  autonumber
  actor U as User
  participant W as Frontend
  participant M as Middleware
  participant S as hrm service
  participant R as record
  participant DB as Postgres
  U->>W: Clicks "Gửi duyệt" (submit for approval)
  W->>M: POST, with the version being viewed
  M->>M: Session, enabled products (write class)
  M->>S: Calls the service, context carries the DB
  S->>DB: BEGIN (InTx)
  S->>R: Transition(ref, version, posted)
  R->>DB: FOR SHARE the legal entity's period-lock row
  R->>DB: FOR UPDATE the document row, compare version
  R->>R: Can, period lock, approval gate, OnTransition
  S->>DB: Write hrm tables
  S->>DB: COMMIT
  S-->>W: Document + allowed_actions + X-Authz-Version
  W->>W: Refresh the cache per the manifest's invalidate
```

- A module calls `record` **before** writing its own tables, in the same transaction ([documents.md](./documents.md#record-functions)).
- The frontend renders buttons from `allowed_actions` and never computes permissions itself ([frontend.md](./frontend.md#permissions-the-frontend-computes-nothing)).

## 6. Document lifecycle

```mermaid
stateDiagram-v2
  [*] --> draft : Create
  draft --> draft : Edit (version increments)
  draft --> [*] : Delete
  draft --> pending_approval : submit, rule requires approval
  draft --> posted : submit, no approval needed
  pending_approval --> posted : last step approved
  pending_approval --> draft : withdrawn or rejected
  posted --> cancelled : cancel
  cancelled --> [*]
```

| Status | In effect | Editable |
| --- | --- | --- |
| `draft` | Not yet | Yes |
| `pending_approval` | Not yet | No |
| `posted` | Yes | No |
| `cancelled` | No longer | No |

- `record` is the only place that holds status. Business progress (delivery, payment…) is the module's own status ([documents.md](./documents.md#document-lifecycle)).

### Lock order

```mermaid
flowchart LR
  l1["1. record.period_locks<br/>the legal entity's row<br/>FOR SHARE (moving the lock date: FOR UPDATE)"]
  l2["2. record.documents<br/>the document row<br/>FOR UPDATE<br/>(Create: numbering counter, then insert)"]
  l3["3. Rows locked by the module<br/>e.g. hrm.payroll_locks, then leave balances"]
  l1 --> l2 --> l3
```

Every document write, period lock and payroll finalization takes locks in exactly this order, so there is no deadlock between them and no new document slips into a period that was just locked. Each transaction writes only one document; bulk operations are jobs that process each document in its own transaction.

## 7. Approval

```mermaid
sequenceDiagram
  actor G as Submitter
  actor D as Approver
  participant R as record
  participant A as approval
  participant H as hrm
  G->>R: Transition(posted)
  R->>A: Approval gate
  A->>H: Approvers(level 1), the record type's callback
  H-->>A: Direct manager
  A-->>R: Approval needed, approval instance I1 (version v)
  R->>R: pending_approval, approval_ticket = I1
  D->>A: Approves the last step of I1
  A->>R: CompleteApproval(I1)
  alt I1 is stale (ticket or version mismatch)
    R-->>A: Rejected, close I1
  else Other error (period lock, OnTransition failed)
    R-->>A: Roll back everything, I1 stays open
  else Valid
    R->>H: OnTransition (e.g. deduct leave balance)
    R-->>A: posted
  end
```

- Each submission is its own approval instance; a late approval of an older submission is rejected ([documents.md](./documents.md#record-functions)).
- Approvers are fixed when a step starts; submitters never approve their own submission.
- `approval` calls `Approvers` through a callback that `hrm` registers with the record type, without importing `hrm`.

## 8. Business lines and posting

```mermaid
flowchart LR
  ot["OnTransition<br/>e.g. payroll to posted"]
  pr["posting.Record / Void<br/>writes posting.lines"]
  hook{"OnChanged hook"}
  job["Reconciliation job<br/>(doc_type, doc_id)"]
  gl[("General ledger")]
  noop["no-op"]
  ot --> pr --> hook
  hook -- "accounting present" --> job --> gl
  hook -- "no accounting yet (current)" --> noop
```

- Business lines are captured once, in the same transaction as the status transition, even before accounting exists ([ADR-0003](./docs/adr/0003-business-lines-are-data.md)).
- Business lines never carry per-person sensitive amounts.

## 9. Enabled products and background jobs

```mermaid
flowchart LR
  op["Operation<br/>route, core route, job"]
  cls{"Operation class"}
  gate{"Product enabled?"}
  perm["Permission check<br/>Can, Scope, sensitive fields"]
  deny["403 product_not_enabled"]
  op --> cls
  cls -- "read, export" --> perm
  cls -- "write" --> gate
  gate -- "yes" --> perm
  gate -- "no" --> deny
```

```mermaid
flowchart TB
  src["Hook, service, periodic job"] --> enq["platform's job-creation function<br/>ProductGate by the job's class"]
  enq --> q[("River queue<br/>in the tenant DB, same transaction")]
  q --> wk["Worker"]
  wk --> sys["System job<br/>system actor, always runs to completion"]
  wk --> usr["User job<br/>re-checks permissions and product when it runs"]
```

- A product that is not enabled, or has been disabled, can still be read and exported ([platform.md](./platform.md#enabled-products)).
- Moving work to the background never escalates permissions ([documents.md](./documents.md#jobs-moving-to-the-background-does-not-raise-permissions)).

## 10. Deployment and tenancy

```mermaid
flowchart TB
  subgraph onprem ["On-premise (primary)"]
    a1["app"] --> d1[("Postgres<br/>1 tenant")]
  end
  subgraph cloudA ["Cloud model A"]
    a2["app"] --> d2[("tenant X")]
    a3["app"] --> d3[("tenant Y")]
  end
  subgraph cloudB ["Cloud model B (later)"]
    reg[("Tenant registry")]
    a4["app<br/>picks the DB by subdomain"] --> d4[("tenant X")]
    a4 --> d5[("tenant Y")]
    a4 --> reg
  end
```

- Each tenant always has its own database; business code is tenant-unaware ([ADR-0001](./docs/adr/0001-one-database-per-tenant.md)).
- The job queue lives in each tenant's database ([ADR-0004](./docs/adr/0004-job-queue-in-tenant-database.md)).
- Moving to model B needs no service changes, because services already take the DB from the context ([tenancy.md](./tenancy.md#cloud-path-from-a-to-b)).

## 11. Frontend

```mermaid
flowchart TB
  main["main.tsx"] --> appf["app<br/>router, shell, manifest wiring"]
  appf --> coref["core<br/>sign-in, administration, approval inbox"]
  appf --> hrmf["hrm<br/>entered through index.ts (manifest)"]
  coref --> sharedf["shared<br/>api, ui, document, auth, i18n"]
  hrmf --> sharedf
  coref -. "does not import hrm;<br/>useRecordLink, RecordPreview<br/>through the recordTypes table wired by app" .- hrmf
```

```mermaid
flowchart LR
  hrmf["hrm area"] --> apicore["shared/api/core"]
  hrmf --> apihrm["shared/api/hrm"]
  hrmf -. "blocked by dependency-cruiser" .-x apiother["shared/api/(other product)"]
```

- Areas never import each other; the boundary is checked on the resolved dependency graph ([frontend.md](./frontend.md#isolation)).
- The cache belongs to a session: a 401, signing out, changing language or a changed `authz_version` clears everything and reloads the page ([frontend.md](./frontend.md#session-lifecycle)).
- Every screen is assembled from the page templates and primitives of `shared/ui` ([ui.md](./ui.md)).
